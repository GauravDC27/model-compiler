Implementation blueprint · drawing set

Goal-Compiled Agentic MoE

A goal compiler turns each request into a typed task graph and a static schedule, deciding every step's executor, token budget, escalation ladder, guards and worst-case cost before anything runs. An assembly of executors runs that schedule: compiled code, System-1 models, classic ML, a Qwen3.6-35B-A3B hub with goal-family capacity, and a Qwen3.8-27B spoke. Everything runs under a compiler-grade determinism contract.

Sheet 01

System overview

Plan §I.0, §I.2

Decisions are made once, at compile time, from calibrated numbers. At run time the system only executes the schedule, checks guards, escalates on calibrated abstention and records everything.

Groq's lesson, transferred

Groq removes runtime arbitration: the compiler decides where and when every operation runs, so latency and cost are known in advance. Agents have data-dependent output lengths, so cycle-exact timing does not transfer. The discipline does: whole-plan analysis, reserved resources, one plan as the source of truth, and explicit guards where data-dependence cannot be avoided.

The user's five items

  • (i) Train discovered experts → hot-expert adapters per goal family (Sheet 05).
  • (ii) New layers and router → goal-gated experts with a compile-time goal bias (Sheet 05).
  • (iii) Specialists and ensembles → spokes, cascades, verifier-selected best-of-K.
  • (iv) System-One models → decision heads, encoders, SLMs and code that abstain upward.
  • (v) Classic ML/DL → GBDT, TabPFN, Chronos-2, kNN and rerankers as registered executors.

Sheet 03

Escalation ladders priced on joint calibration

Plan §I.2.1, §I.2.2 · Outcome, _estimate_joint

A cascade passes its hardest items upward. Multiplying each rung's average accuracy ignores that, so the scheduler replays every candidate ladder item by item on a shared calibration split.

Executor registration contract

  • Input schema compiled from IR slots (feature schema for classic ML).
  • Output is a typed IR value plus a conformally calibrated probability. No executor returns free text into the graph.
  • Cost model: coverage, accuracy, forced accuracy, token bounds, input reads, latency, version, plus per-item Outcome records.
  • Contract D0 or D1, a lock, and a minimum calibration size per (op, difficulty) bucket.

Bounds versus expectations

Executor token fields are compiled bounds: fixed prompt size, decode budget, and how many times the node's capped input is read (0 for code, 2 for two-order label scoring). Expected tokens come from what calls actually spent on calibration items.

Pilot 07 tests whether the joint prediction transfers to a held-out split. If it does not, bars are compared against the Wilson lower bound instead of the point estimate.

Sheet 04

Guards, variants and recompiles

Plan §I.2.1 · Guard, Program, GuardRuntime

Data-dependent branches are handled the way a JIT handles deoptimization. Likely alternatives are compiled in advance, guards check typed outputs, and every path out of the plan is counted against the bound or ends in a defined failure.

Sheet 05

Inside the hub: one MoE layer with goal capacity

Plan §I.2.3 · dmc/expansion.py, dmc/expert_lora.py

The goal enters the hub as a bias on the router, set by the compiler before the request runs. For the goal's family it opens trained goal experts. For every other family the bias is −∞, so those goal experts are never selected. With no goal set, the layer is the base layer itself and its output is bit-identical by construction.

Item (i): train the discovered experts

A routing atlas on each family's traffic, measured on hub-base, finds the hot experts by selection counts (A3B rule: 80% of overall mass ∪ 50% per slice; about 97 of 256 per layer for voice). They get a rank-16 LoRA whose B matrix starts at zero, so attaching it changes nothing until training moves it. Ablations: experts-only, and ESFT-tight sets of 5–15% of experts.

Item (ii): new experts and router

New experts are warm-started as copies of the family's hottest expert, with router rows copied from the parent. Noise (σ = 0.05·std) goes on the copy only, so the parent is never perturbed. Only the new experts, their rows and the goal biases train. A router-only review pass on less than 1% replay protects retention (MoE-LPR: 96.6% with it, about 87% without).

Guarantee, and how it is tested

With the goal off, the wrapped block returns base(h) itself, so the result is bit-identical by construction (tests/test_expansion.py). Pilot 06 compares routed and additive experts against a matched-rank LoRA arm, a router-only arm and a random-parent arm, and also measures accuracy when the goal is wrong.

Sheet 08

Cost feasibility model

Plan §I.1.1

At accuracy parity, cost-of-pass relative to the 27B = r·τ_h + e + s, where s, the cost of System-1 executors and code, is close to 0. The hub's per-token cost r is measured in G0. τ_h is hub verbosity relative to the 27B, and e is the escalation budget. The targets are read off this chart, not asserted.

Trust layer: replay and contracts

Plan Part II · R1–R28

The same canonical input, session state and lock always produce the same bytes. A first execution runs only on an executor whose contract meets what the node requires, and it is recorded so later requests replay it.
